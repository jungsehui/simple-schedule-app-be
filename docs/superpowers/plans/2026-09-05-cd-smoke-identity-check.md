# CD 스모크 확장 — 배포된 것이 방금 만든 것인지 확인한다

**Goal:** 스모크가 "옛 이미지가 그대로 떠 있는" 상태를 통과시키지 못하게 한다.

**착수 전 상태:** 계획만. 오너 승인 대기.

---

## 문제 — 두 릴리스 연속으로 확인된 것

현재 스모크(`deploy.yml:195-205`)는 이것 하나다.

```bash
curl -o /dev/null -w "%{http_code}" "http://localhost/lectures/search?keyword=smoke"
# 401이면 통과
```

**이 검사는 "nginx가 백엔드에 닿는다"까지만 본다.** 배포가 실패해 옛 컨테이너가 그대로 떠 있어도 401은 나온다. 즉 **릴리스가 실제로 반영됐는지는 검증하지 않는다.**

2026-09-04 릴리스에서 실측으로 확인했다. 스모크는 초록이었고, 그와 별개로 내가 WireGuard로 붙어 새 정규식이 살아 있는지를 직접 확인해야 했다.

## 무엇을 검증해야 하는가 — 문제를 다시 정의한다

"릴리스가 바꾼 동작을 스모크가 검증하게 하자"가 첫 생각이었다. **그건 문제를 잘못 잡은 것이다.**

릴리스마다 바뀌는 동작이 다르므로 검사도 릴리스마다 고쳐야 한다. 고치는 걸 잊으면 검사는 옛 동작을 보며 초록을 낸다. 그리고 어떤 릴리스는 무토큰으로 확인 가능한 동작 변화가 아예 없다.

**진짜 물어야 할 것은 동작이 아니라 신원이다.**

> CI는 이미 SHA X의 코드를 테스트했다. 스모크가 증명할 것은 **지금 돌고 있는 프로세스가 X인가**뿐이다.

신원이 맞으면 동작은 CI가 보증한다. 이 재정의로 검사가 릴리스마다 손볼 필요가 없어진다.

## 해법 — 애플리케이션을 건드리지 않는다

CD가 **이미 이미지를 SHA로 태깅**하고 있다.

```
deploy.yml:92   .../ssa-${{ matrix.module }}:${{ github.sha }}
deploy.yml:171  IMAGE_TAG=${{ github.sha }} docker compose ... pull
```

그러므로 배포 호스트에서 실행 중인 컨테이너의 이미지 태그를 읽어 `github.sha`와 대조하면 된다.

```bash
running=$(docker inspect --format '{{.Config.Image}}' ssa-app | awk -F: '{print $NF}')
[ "$running" = "${{ github.sha }}" ] || { echo "::error::배포된 이미지가 이번 커밋이 아니다: $running"; exit 1; }
```

**앱 코드 변경 0, 새 엔드포인트 0, 노출 위험 0이다.**

### 기각한 대안과 이유

| 대안 | 기각 이유 |
|---|---|
| `/actuator/info`에 빌드 SHA 노출 | 빌드 정보 생성 설정을 새로 넣어야 하고(`buildInfo()` 없음, 지금 `info`는 비어 있다), 인증 게이트 통과 여부를 정해야 하며, **nginx가 `/actuator`를 막지 않는다**(`/internal/`만 차단). 배포 SHA를 외부에 흘릴 수 있다 |
| 릴리스가 추가한 경로의 401 확인 | 릴리스마다 손봐야 하고, 경로를 추가하지 않는 릴리스에는 쓸 수 없다 |
| 릴리스가 바꾼 동작을 직접 확인 | 위와 같은 문제 + 무토큰으로 확인 불가능한 변경이 많다 |

## 두 검사를 함께 둔다 — 각각 다른 것을 증명한다

| 검사 | 증명하는 것 |
|---|---|
| 이미지 태그 대조 (신규) | 컨테이너가 **이번 커밋의 이미지**로 만들어졌다 |
| `/lectures/search` → 401 (기존) | 그 프로세스가 **실제로 서빙 중이고** nginx가 닿는다 |

**하나만으로는 부족하다.** 이미지만 보면 컨테이너가 크래시 루프 중이어도 통과하고, 401만 보면 옛 이미지가 통과한다. 둘을 함께 둬야 "새 코드가 서빙 중"이 된다.

## 2026-09-12 릴리스의 실측 데이터

이 계획을 쓴 뒤 릴리스가 한 번 더 있었다(main `f27d148`). 거기서 내가 **손으로** 돌린 검증이 이랬다.

```
DELETE /special-lectures/1/enrollments  → 401   (이번 릴리스가 추가한 경로)
DELETE /this-route-does-not-exist       → 404   (양성 대조)
```

없는 경로가 404를 준다는 것을 먼저 보였기 때문에, 신규 엔드포인트의 401이 "라우팅이 실재한다"의 증거가 됐다. 옛 이미지였다면 404였다. **계정 없이 새 이미지 생존을 증명했다.**

### 그래서 이걸 CD에 넣어야 하나 — 아니다

이 방법이 통한 것은 사실이고, 그 자체로는 좋은 판별이다. 하지만 **자동화 대상은 아니다.**

| 문제 | 내용 |
|---|---|
| 릴리스마다 손봐야 한다 | 대상 경로가 매번 다르다. 고치는 걸 잊으면 옛 경로를 보며 초록을 낸다 |
| 쓸 수 없는 릴리스가 있다 | 이번 릴리스는 마침 경로를 추가했다. 버그 수정만 있는 릴리스에는 **무토큰으로 확인할 신규 경로가 없다** |
| 양성 대조가 함께 있어야 한다 | 401/404 판별은 "없는 경로가 404"를 같이 보여야 성립한다. 자동화하면 그 짝을 유지하는 부담이 는다 |

**"릴리스 PR 본문에서 대상 경로를 읽는다"는 방식도 기각한다.** PR 본문은 산문이고 형식 보장이 없다. 본문을 잘못 쓰면 검사가 조용히 빈 문자열을 치게 되는데, 그건 **명령이 실패했을 때 통과하는 검사**다. 이 저장소가 두 번 데인 바로 그 형태다.

### 정리: 자동화는 신원, 손검증은 동작

| 무엇 | 어디서 | 왜 |
|---|---|---|
| 이미지 신원 대조 | **CD 스모크 (자동)** | 릴리스와 무관하게 항상 같은 검사. 손볼 일이 없다 |
| 신규 경로 401/404 | **배포 후 손검증 (사람 또는 에이전트)** | 릴리스마다 다르고 판단이 필요하다 |

신원이 맞으면 동작은 CI가 보증한다. 손검증은 그 위에 얹는 확인이지 대체물이 아니다.

## 검증 — 이 검사가 실제로 무언가를 잡는지

**반증이 필수다.** 이 검사 자체가 "돌지만 대상을 못 보는" 부류가 되기 쉽다.

1. `github.sha` 대신 존재하지 않는 SHA를 넣어 스텝이 **실패하는지** 확인한다. 통과하면 비교가 성립하지 않는 것이다(태그 파싱 실패로 양쪽이 빈 문자열이 되는 경우가 흔하다).
2. `docker inspect`가 반환하는 형식을 **실제 배포 호스트에서 한 번 눈으로 확인**한다. `ssa-app` 컨테이너명과 이미지 태그 형식이 가정과 같은지 본다. 이름이 다르면 `inspect`가 실패하고, 그 실패가 "이상 없음"으로 둔갑하지 않도록 `set -e`와 빈 값 검사를 함께 둔다.

**빈 값 통과를 막는 것이 핵심이다.** `[ "$running" = "$expected" ]`에서 둘 다 빈 문자열이면 참이 된다. 명령이 실패했을 때 통과하는 검사는 없는 것보다 나쁘다.

## 남기는 것

- **geekchat 컨테이너**도 같은 방식으로 대조할 수 있다. 다만 그쪽은 SSA와 릴리스 주기가 달라 SHA가 다를 수 있으므로, 대조 대상을 `ssa-app`으로 한정한다.
- 이 검사는 **롤백을 감지하지 못한다.** 수동 롤백 후 스모크를 다시 돌리면 "이번 커밋이 아니다"로 실패한다. 롤백 절차에서는 이 스텝을 건너뛰어야 한다 — 런북에 적을 것.
