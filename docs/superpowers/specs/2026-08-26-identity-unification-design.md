# 회원 단일화 설계 — 역할 모델과 username 정책

- 상태: 설계안 (오너 승인 대기)
- 날짜: 2026-08-26
- 관련: ADR-0003 Stage 5, ADR-0005, `orchestration/IDENTITY-UNIFICATION-BRIEF.md`
- 선행: `2026-08-26-identity-unification-verification.md` (검증 1·2차)

> **이 문서는 ADR-0003 Stage 5가 답하지 않은 두 가지만 다룬다.** 나머지(식별자 이중 키,
> 인증 스택, 시크릿, 스키마, 비밀번호)는 이미 결정돼 있고 검증 보고서에서 성립을 확인했다.

## 전제 (실측 확정)

| 사실 | 근거 |
|---|---|
| 실사용자 **0명**. 양쪽 14계정 전부 오너 테스트 계정 | 오너 확인 2026-08-26 |
| username 충돌 3쌍은 **같은 사람** — 병합 승인됨 | 오너 확인 |
| SSA 서브타입이 담는 것은 **스칼라 하나씩** | `Student.school` / `Tutor.careerPeriod` / `Parent.childrenNumber` |
| geekchat `UserRole`은 역할이 아니라 **기능 플래그** | `UserRole.kt` 주석: *"ADMIN unlocks AI chat; USER is human-to-human only"* |

## 1. 역할 모델 — 계정 레벨과 제품 레벨을 분리한다

### 왜 이게 답인가

두 "역할"은 **경쟁하는 enum이 아니라 다른 축**이다.

| | SSA `Role` | geekchat `UserRole` |
|---|---|---|
| 값 | STUDENT / TUTOR / PARENT | USER / ADMIN |
| 성격 | **과외 도메인에서 무엇인가** — 어떤 엔드포인트·어떤 캘린더인지 결정 | **기능 플래그** — AI 채팅 해금 여부 |
| 통합 후 자리 | `member` (SSA 도메인 소속) | `users` (채팅 프로필) |

합치려 하면 geekchat 사용자가 어느 서브타입에도 안 맞는 문제가 생기는데, **애초에 맞을 필요가 없다.** ADR-0003 결정 3이 claims를 `role`+`admin`(별도 boolean)으로 나눈 것이 이미 이 구분을 반영한다.

### 구조

```
account  (Long id, external_uuid, username, password_hash, ...)   ← 정체성 + 자격증명
   │
   ├─ 0..1 ─→  member  (member_id = account.id)   ← SSA 도메인 소속. JOINED 상속 유지
   │                     Student/Tutor/Parent
   │
   └─ 0..1 ─→  users   (id = external_uuid)        ← 채팅 프로필. role=USER/ADMIN
```

**상속을 유지하는 이유:** 서브타입이 스칼라 하나씩만 담아서 해체 이득이 작은데, 잃는 것(타입 안전성, `getRole()`의 컴파일 타임 보장)은 실질적이다. 해체하면 `school`·`careerPeriod`·`childrenNumber`가 전부 nullable이 되고 "어떤 조합이 유효한가"가 코드에서 사라진다.

**두 관계가 모두 `0..1`인 것이 핵심이다.** 채팅만 쓰는 계정도, 과외만 쓰는 계정도 정당하다.

### JWT claims (ADR-0003 결정 3 준수)

```
sub       = account.id (Long)
memberId  = account.id (Long)   ← 기존 클라이언트 호환. /login 응답 불변
role      = member.role         ← member 행이 없으면 클레임 자체가 없다
admin     = users.role == ADMIN ← 없으면 false
```

`LoginResponse{memberId, accessToken, role}`은 **모양이 안 바뀐다.** SSA 회원이 아닌 계정이 SSA `/login`으로 들어오는 경우가 없으므로(그쪽은 채팅 로그인), 기존 응답은 그대로다.

## 2. 🔴 T8이 Stage 5와 충돌한다 — 새 코드가 필요하다

### 문제

통합 후 **채팅만 쓰는 계정**이 생긴다. `member` 행이 없으니 토큰에 `role` 클레임이 없다. 그 토큰으로 SSA 엔드포인트를 부르면 어제 도입한 코드가 나온다:

```
403 T8 REQUIRED_ROLE_CLAIM  "역할 정보가 없는 토큰입니다. 다시 로그인해 주세요."
```

**정상 로그인한 사용자에게 재로그인을 시킨다. 다시 로그인해도 여전히 회원이 아니라 같은 응답이 나온다 — 무한 루프다.**

T8의 전제가 *"역할 없음 = 망가진 토큰"*인데, 통합 후에는 *"역할 없음 = 이 계정은 과외 서비스 회원이 아님"*이 **정당한 상태**가 된다. **같은 코드가 다시 두 원인을 덮는다** — T6에서 갈라낸 것과 정확히 같은 형태다.

### 해소 — 서버가 구분할 수 있다

`sub`로 계정을 찾으면 `member` 행 존재 여부를 알 수 있다.

| 상황 | 코드 | 클라이언트가 할 일 |
|---|---|---|
| `member` 있는데 토큰에 `role` 없음 | `403 T8` REQUIRED_ROLE_CLAIM | **재인증** (통합 이전 발급 토큰) |
| `member` 없음 | **`403 T9` MEMBER_PROFILE_REQUIRED** | **회원 가입 유도** — 재인증이 아니다 |

코드값은 `T9`다. `T7`은 폐기·재사용 금지이고 `T8`은 어제 썼다.

상태코드는 **둘 다 403**을 유지한다. 인증은 됐고 자격이 없는 상태라 403이 맞다.

### ⚠ T9는 UX 주 경로가 아니라 **서버 측 백스톱**이다

클라이언트는 **토큰(또는 `/login` 응답)에 `role`이 없다는 사실만으로 채팅 전용 계정임을 선제적으로 안다.** 그러니 SSA 화면을 아예 게이팅하면 된다 — Android가 `/me/lectures`에서 이미 확립한 패턴(*"권한 없는 역할에는 아예 호출하지 않는다"*)과 같다.

**T9는 그 게이팅이 뚫렸을 때만 나온다.** 기본 차단 원칙과 정합하고, 클라이언트가 새 에러 분기를 UX에 배선할 부담도 없다.

계약서에 이렇게 적어야 한다: *"클라이언트는 `role` 클레임 부재로 게이팅하라. `T9`는 그 게이팅이 실패했을 때의 서버 백스톱이며, 이 코드를 UX 흐름의 주 경로로 삼지 말 것."*

### ⚠ 이 테스트는 Stage 5와 같은 커밋에 들어가야 한다

**Stage 5 이전에는 `member` 없는 계정이 존재할 수 없다** — SSA 토큰은 회원가입 경로에서만 나오기 때문이다. 즉 T9는 도달 불가능하고, 미리 쓴 테스트는 **통과하지만 아무것도 검증하지 않는다.**

> 판별 질문: *"내가 막으려는 바로 그 사고(채팅 전용 계정의 SSA 호출)에서 이 검사가 실패하는가?"*
> Stage 5 이전에는 **아니오**다.

`extractRole()`의 `Role.valueOf` 500 위험도 같은 성질이라(시크릿 통일 전에는 서명에서 끊긴다), **두 테스트는 함께 Stage 5 커밋에 들어간다.**

## 3. username 정책

### 3-1. `account.username`에 유니크를 건다

**양쪽 다 `username`+`password`로 로그인한다**(SSA `LoginRequest`, geekchat `AuthDto.kt:38`). username이 두 시스템 모두에서 자격증명이므로, 계정이 로그인 단위가 되는 순간 계정 레벨 유니크가 **필수**다.

`NULL`은 허용한다 — OAuth 가입자는 username 없이 들어온다(`CompleteOAuthSignupRequest`에 username 필드가 없다). PostgreSQL은 유니크 제약에서 다중 `NULL`을 허용하므로 이게 정확히 원하는 동작이다.

### 3-2. 통합 규칙: `^(?=.*[a-z])[a-z0-9_]{3,20}$`

**어느 한쪽을 고른 게 아니라, 양쪽의 안전 속성을 각각 취했다.**

| 속성 | 출처 | 왜 |
|---|---|---|
| **소문자만** | geekchat | 대문자를 허용하면 `Admin` vs `admin` **사칭 가능성**이 생긴다. 자격증명에서 대소문자 변형은 위험만 있고 이득이 없다 |
| **영문자 1자 이상 필수** | SSA | 전부 숫자인 username(`12345`)은 **`memberId`와 혼동**된다. URL·로그·지원 문의에서 실제로 헷갈린다 |
| **밑줄 허용** | geekchat | 무해하고 이미 쓰인다 |
| **최소 3자** | geekchat | 4자를 요구할 안전상 근거가 없다. 넓은 쪽을 택한다 |

기존 값 호환을 고려하지 않은 이유는 **실사용자가 0명**이기 때문이다. 지금이 규칙을 옳게 정할 수 있는 유일한 시점이다.

> 좁히는 변경은 파괴적이고 넓히는 변경은 추가형이다. 지금 좁은 쪽으로 정해 두면 나중에 넓힐 수 있지만, 넓게 시작하면 되돌릴 수 없다.

**입력 정규화:** 저장 전에 소문자로 변환한다. 규칙이 소문자만 허용하므로 대문자 입력은 거부가 아니라 정규화가 맞다 — 사용자가 `Abc12`를 치면 `abc12`로 로그인된다.

### 3-3. 충돌 3쌍 — 병합. 그런데 우연이 아니다

오너가 같은 사람으로 확인했다. 계정 1행이 `member` 1행과 `users` 1행을 함께 가리킨다. **데이터 이동 없이 참조로 잇는다**(ADR 결정 2의 이중 키가 그걸 가능하게 한다).

**왜 3쌍이 겹쳤는지 원인을 찾았다.** 웹에 `lib/chat-bridge.ts`가 있고, 파일 헤더가 스스로를 이렇게 설명한다:

> *"SSA 로그인/가입 성공 시 동일 자격증명으로 chat 세션을 자동 확보한다. (…) **BE 인증 통일이 배포되면 이 파일은 제거된다.**"*
> *"username 매핑: SSA는 대소문자 허용, chat은 소문자만 → lowercase 매핑. **충돌(409) 시 `_ssa` 접미사로 1회 재시도.**"*

즉 **이 브리지가 섀도 계정을 만들고 있고, 그게 Stage 5가 청소할 대상이다.** 3쌍은 우연한 동명이 아니라 **설계된 쌍**이라 "같은 사람"이 구조적으로 보장된다.

### 🔴 3-3-1. 그래서 마이그레이션에 구멍이 하나 있다

브리지는 두 갈래로 동작한다:

| 경우 | 결과 | username 대조로 찾히는가 |
|---|---|---|
| lowercase 매핑 성공 | `foo`(SSA) ↔ `foo`(chat) | ✅ 찾힌다 — 실측 3쌍이 이것 |
| **409 충돌 → `_ssa` 폴백** | `foo`(SSA) ↔ **`foo_ssa`**(chat) | ❌ **못 찾는다** |

**`username` 일치로 짝을 찾는 마이그레이션은 폴백 케이스를 통째로 놓친다.** 놓치면 같은 사람에게 계정이 둘 생긴다.

> 이건 STEP 4에 적어 둔 한계(*"username 겹침 ≠ 같은 사람, 0건 ≠ 없음"*)의 반대 방향 사례다. 그때는 "찾은 것이 같은 사람이 아닐 수 있다"였고, 이번은 **"같은 사람인데 못 찾는다"**이다.

**계획서 필수 항목:** 백필 전에 `_ssa` 접미사 계정을 별도로 조회해 짝을 확인한다.

```sql
-- geekchat 쪽에 _ssa 폴백으로 만들어진 계정이 있는가
SELECT g.username AS chat_username, m.username AS ssa_username
FROM geekchat.users g
JOIN ssa.member m ON g.username = m.username || '_ssa';
```

0건이면 폴백이 한 번도 안 탔다는 뜻이라 username 대조만으로 충분하다. 0건이 아니면 그 짝들도 병합 대상이다.

### 3-4. 앞으로 충돌을 어떻게 막는가

통합 후에는 `account.username` 유니크 제약이 **구조적으로** 막는다.

**전환기(듀얼라이트)가 위험 구간이다.** 두 시스템이 각자 쓰기를 받는 동안에는 각 테이블의 유니크만으로는 교차 충돌을 못 막는다.

> **전환기 제약:** 어느 쪽 시스템의 회원가입이든 **`account` 유니크를 먼저 확인한 뒤** 자기 테이블에 쓴다. `account` 삽입이 실패하면 가입도 실패한다.

이게 성립하려면 `account`가 **듀얼라이트의 시작점**이어야 한다. 계획서에 순서 제약으로 넣는다.

## 4-1. username 규칙은 클라이언트 계약 변경이다 — 동시 갱신 목록

정규식을 바꾸면 클라이언트 검증이 서버와 어긋난다. **계획서에 이 목록을 박는다:**

| 위치 | 현재 | 조치 |
|---|---|---|
| 웹 `app/signup/page.tsx:84` | zod가 구 정규식 미러(`^(?=.*[a-zA-Z])[a-zA-Z0-9]{4,20}$`) | 새 규칙으로 |
| 웹 `lib/chat-bridge.ts` | **파일 전체가 섀도 계정 브리지** | **Stage 5로 소멸한다** — 파일 헤더가 스스로 그렇게 적고 있다. 삭제 시점을 계획에 명시 |
| Android signup 검증 | 구 정규식 | 새 규칙으로 |
| `API-CONTRACT.md` §2 | Bean-Validation 미러 목록 | 내 구역 — 내가 갱신 |

`chat-bridge.ts`는 단순 갱신이 아니라 **삭제 대상**이다. 규칙이 통일되면 lowercase 매핑도 `_ssa` 폴백도 존재 이유가 없다.

- **Stage 5 실행 순서와 Flyway 단계** — `writing-plans`의 몫이다
- **ADR-0003 결정 3의 종착점 정정**(`@PreAuthorize` fail-open) — 검증 2차에 기록했고, 구현 시 ADR 정정으로 다룬다
- **공개 접점(TLS/도메인)** — 별건. 도메인 결정 대기 중

## 7. 이 설계에서 얻은 규칙 — 에러 코드는 세계 가정을 인코딩한다

`T8`은 **어제의 세계에서는 옳았다.** "역할 없음 = 망가진 토큰"이 그때는 참이었다(발급 4경로가 전부 role을 넣고, 구 토큰은 만료됐다).

Stage 5가 그 가정을 바꾼다. **"역할 없음"에 정당한 새 의미(채팅 전용 계정)가 생기고, 그 순간 T8은 두 원인을 덮는다.**

> **규칙: 에러 코드는 세계에 대한 가정을 인코딩한다. 세계를 바꾸는 설계는 에러 코드 표 전체를 재감사해야 한다.**

이번 설계에서 그 재감사로 T9가 나왔다. `T0`~`T6`도 같은 눈으로 훑었고, 나머지는 통합 후에도 의미가 유지된다(토큰 부재·만료·서명 실패는 세계와 무관하다).

판별 질문과 짝이 되는 형태다 — 판별 질문이 *"이 검사가 그 사고에서 실패하는가"*를 묻는다면, 이 규칙은 *"이 코드가 전제하는 세계가 아직 참인가"*를 묻는다.
